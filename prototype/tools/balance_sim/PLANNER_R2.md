# planner 第2段：山場と学習

Nodeの検証ツールだけ。戦闘・敵生成・報酬生成・交換・指輪・祝福は本体を呼ぶ。第1段の役割抽出・型の更新は[PLANNER.md](PLANNER.md)を引き継ぐ。前回outは全32ファイルを `out_planner_r1/` へ保存し、バイト一致を確認した。

## 実行

```sh
node tools/balance_sim/planner_tune.js --workers 4
node tools/balance_sim/run_bot.js --runs 200 --policy lookahead,planner --seed 4001 --workers 4 --out tools/balance_sim/out
node tools/balance_sim/run_bot.js --runs 200 --policy planner --planner-stage r1 --seed 4001 --workers 4 --out tools/balance_sim/out/r1_evaluation
node tools/balance_sim/run_bot_selftest.js --input tools/balance_sim/out --variant tools/balance_sim/out/r1_evaluation
node tools/balance_sim/run_report.js --input tools/balance_sim/out
```

`--planner-stage r2` が既定。`--planner-weights <json>` は `{ "weights": { ... } }` の係数をラン単位で適用する。指定しなければ学習済み `planner_weights.json` を読む。第1段は元の係数を固定して保持する。周回行にも適用した全係数と段階を保存し、再現検査はその値を使う。所要時間はJSONLには含めない。

## 山場

`planner_horizon.js` は本体の旅程から次のエリート/ボスと、そこまでの通常戦報酬・街の交換を数える。通常戦は勝利後のstageで報酬を抽選する。エリート/ボスに通常報酬を追加しない。現在表示中の店や報酬は、候補に含めたうえで未来の機会には二重計上しない。

未戦闘の敵は `enemySamples` の別系列 `planner-wall` から2例を本体で生成する。再戦では本体が保存した既知の敵を使い、戦闘乱数だけを別系列にする。サンプルのキャッシュには既知の敵の内容、コアのキャッシュには種だけでなく敵の全データを含める。次戦評価は元の3例。G、提示、開戦状態、Math.randomを隔離し、ランの乱数を消費しない。同一プロセス内では直列。

次戦点で上位3候補を残し、役割までの評価で首位だった候補と任意選択の見送りも追加する。指輪が必須の場面に見送りはない。それぞれについて、将来カードなし35%、独立した実提示列2通りを各32.5%で試す。実提示は本体 `drawRewards` で、在庫・出現率・保証・祝福を本体が処理する。提示からsynergyの役割と現在の型に合う合法配置を選び、通常戦1回につき最大1枚を本体 `takeRewCard`、未来の街は `exchangeShopCard` で交換する。想定盤面の配置は共通 `policies.arrange` の合法スワップを1巡だけ使う。

合計点は `next × 次戦点 + fit × 既存相乗 + option × 入手見込み + focus × 型への近さ + 祝福の将来価値 + 山場点`。次戦点は240×勝率＋40×残HPの対数＋4×与ダメージの対数。ライフ1は勝率400。山場点は `(wall × 勝率 + wallHp × 残HPの対数 + wallProgress × 敵HP減少率) / (1 + distanceDecay × 山場までの通常戦数)`。HPの規模を揃える分母はmax(40,敵HP)。敵HP減少率は1−残敵HP/敵開始HPを0〜1へ丸め、勝利時は1。全想定が敗北して味方HPが0でも、壁へ近づく選択に補助点を付ける。係数の決定値はJSONを唯一の入力とする。

盤面・指輪・道具・永続強化・祝福・資金等が同じコア試行はキャッシュする。キャッシュと統計はランごとに破棄する。実行した選択の `horizonDecision`、コアの予測値と想定盤面、上限12件の変更例をJSONLへ保存する。報告には選ばなかった旧首位も同じサンプルで試した結果を出す。この比較は同条件の予測であり、代替を選んだラン全体の実測ではない。

道具は想定を作る前に実際と同じ使用方針で消費する。巨大化などの永続変更を、まだ拾っていない未来の本体へ付けない。途中の通常戦を越える時には本体 `_prepareStartingBattleItems(false)` を呼び、隕石・沈黙などの次戦限りの効果をその戦闘へ送る。山場の trial はもう一度同じ本体の準備を通すため、途中で使った一時効果は山場へ持ち越されない。山場が次戦なら一時効果も残す。想定のqueuedItemsも記録する。

## 学習

`planner_tune.js` は種1001〜1040だけを使う。8組の係数を共通10種、上位3組を共通20種、上位2組を共通40種で比較する。目的値は `mean(reachedWave + reachedStage / 100) + 2 × clearRate`、同点なら平均到達St、その次はIDの辞書順。10/20種で敗退した候補も含め、試した係数・成績・時間を `out/training/weight_search.csv` へ全件保存する。既に計算した種を再利用し、1回の探索は合計150周。探索から決まった値をJSONへ保存してから最終評価種4001〜4200を使う。予備探索は `out/training_initial/` に残し、全敗時の補助点と将来の報酬機会を修正した。

これは少数候補による自動選択で、連続空間の最適値の保証はない。8候補の範囲・山場のサンプル数・35%の追加取得なし率等は探索外の近似定数。新たにモデルを調整する場合は学習用の種で行い、見てしまった評価用の種を再び未使用と呼ばない。

種2001〜2200の最初の比較は `out/r2_initial/` へ保存する。その実例で一時的な道具の持越しを発見し修正した。種3001〜3200でも到達が改善せず、再戦で山場側だけ別の敵を使う入力の不整合を確認したため、既知の敵とキャッシュの鍵を修正した。この比較は `out/r2_before_retry_fix/` へ保存する。最終検証には新たな種4001〜4200を使い、診断に使った過去2組を未使用とは扱わない。探索4回、合計600周の経過を残す。

## 検査と診断

`planner_horizon_selftest.js` は山場の旅程、独立乱数、予測の実行、実周回で選択が変わったこと、40種の学習と200種の分離を検査する。`run_bot_selftest.js` は全件監査と同じ種の全JSON一致を引き続き行う。主要カード抽出・第1段の将来投資の制御例も残す。

`planner_r2_report.js` が三方針の同種比較、難易度曲線、型の完成分布、重み探索、先読みが変えた選択、想定/実際の盤面の差を出す。後半の初戦率は到達者だけを母数にする。型の完成は静的な役割照合で発動量を保証しない。未来の報酬は本体の実抽選だが、途中戦闘の死亡/永久強化/敗北、未来の道具購入・祭壇交換を完全に再演しない。元の役割だけの入手確率は独立枠近似のまま併用する。
